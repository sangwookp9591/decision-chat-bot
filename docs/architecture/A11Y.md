# 접근성·반응형 브라우저 검증

T23의 재현 가능한 브라우저 검증은 `frontend/e2e/a11y/a11y.spec.ts`와 `frontend/playwright.a11y.config.ts`에 있다. 실제 로그인 세션과 실제 API 데이터를 사용하며, 주요 화면의 axe 검사에서는 critical/serious 위반만 게이트로 취급한다.

## 실행

Neo4j, API, worker를 실행한다. E2E 전용 tenant를 만들고 개발 역할 계정을 준비한 뒤 worker에는 그 tenant만 전달한다. WebKit 브라우저 설치는 `cd frontend && npx playwright install webkit`으로 한다.

```sh
make up
cd backend
.venv/bin/python ../scripts/bootstrap_dev.py
.venv/bin/uvicorn jevtriage.main:app --host 127.0.0.1 --port 8147
```

별도 터미널:

```sh
cd backend
.venv/bin/python -m jevtriage.jobs.worker --tenant <E2E 전용 tenant>
```

프런트 검증:

```sh
cd frontend
E2E_API=http://127.0.0.1:8147 E2E_PORT=5281 npx playwright test --config=playwright.a11y.config.ts
```

기본 Playwright 설정도 Chromium과 WebKit 프로젝트를 제공한다. 테스트 계정 암호를 바꿨다면 `JEVTRIAGE_DEV_PASSWORD`에 지정한다. 전용 tenant의 로그인 계정도 `requester`, `reviewer` 역할별로 준비한다.

## 검사 범위

- 로그인 및 요청 접수, 검토, 업무, 실행 관찰, 판단 맵 입체/목록, 규칙 학습, 모니터링, 정책 화면의 axe WCAG 2.1 A/AA 검사
- ChatWidget 열기와 요청 제출의 키보드 조작, 모달 포커스 순환, Esc 닫기와 초점 복귀
- 판단 맵 목록의 화살표 이동과 Enter 선택, 실요청 제출 후 원문 근거 열기
- 사이드바 고정/상단 메뉴 전환과 가로 overflow: 1280/960/520/375px
- ChatWidget 520px 전체 화면, 대표 버튼·메뉴의 44px 터치 영역, Primary 버튼 글자색
- reduced-motion 정지 PNG, WebKit/Safari의 WebP 선택, 화면 내 디자인 샘플 문자열 및 mock 표시 확인

브라우저 검증 스크린샷과 실행 결과는 `artifacts/validation/t23/`에 보관한다. 실데이터에는 사용자 원문이 포함될 수 있으므로 저장하는 스크린샷은 실행 전용 tenant의 비민감 검증 요청으로 한정한다.

## UX-1 화면 동작 기준 (브라우저 탐색 P3-01~P3-13 수정)

- **로그인**: 이메일·암호 입력과 제출 버튼이 있으며 오류는 `role="alert"`로 한국어 안내한다(401 잘못된 정보, 429 시도 제한). 성공해도 URL을 바꾸지 않으므로 처음 요청한 경로가 그대로 열린다.
- **URL이 상태를 가진다**: 요청 접수 `/?request_id=`, 검토 `/review?request_id=|review_id=`(처리 완료 검토도 열림, 결정 버튼은 읽기 전용), 실행 관찰 `/observatory?request_id=&run_id=`. 새로고침·뒤로가기·공유 링크로 같은 대상을 복원한다.
- **정보 요청**: 요청 상태가 '보완 필요'이면 검토자의 사유·필요 정보를 표시하고 같은 요청의 새 revision으로 보완 제출한다(`expected_revision` 포함). 결과 배지는 요청 상태(보완 필요·반려됨·배정 완료)를 우선하고, 검토 결정 SSE(`review_decided` 등)로 갱신한다.
- **일동이 대화(CHAT-1)**: 떠 있는 위젯·런처는 없다. 요청 접수 화면 자체가 대화이며 대화 영역은 `role="log" aria-live="polite"`(`aria-label="일동이와의 대화"`), 입력창은 `요청 내용` 레이블, Enter 전송(IME 조합 중 제외)·Shift+Enter 줄바꿈, 파일 첨부 input은 탭 순서에 유지한다. 말풍선은 `role="group"`과 이름(내가 보낸 요청·분석 진행·일동이의 답변·읽기 실패 파일·보완 요청)을 갖고, 결과 상태는 아이콘뿐 아니라 문장('확인이 조금 필요해요', '긴급 요청이에요')과 배지 글자로도 전달한다. 긴급 결과는 마스코트 대신 경고 표식, reduced-motion에서는 wave 대신 정지 PNG. 대화 목록은 960px 이하에서 `aria-expanded` 토글로 접힌다.
- **입력 방해 금지**: 정책 JSON 편집기는 필드별 원문 초안을 유지하고 마지막 유효 값만 설정에 반영한다. 모니터링 기간은 초안/적용을 나누고 빈 값·역순은 입력 오류로 안내하며 조회하지 않는다.
- **한국어 라벨**: 역할·상태·검토 동작·첨부 읽기 실패 사유·서버 오류는 `components/statusLabels.ts`의 `roleLabel`·`statusText`·`reviewActionLabel`·`attachmentReasonLabel`·`localizeError`를 공용으로 쓴다. 내부 코드는 '기술 상세'(`<details>`)에만 둔다.
- **375px**: 요청 화면은 입력을 목록보다 먼저 두고 상태 배지는 줄바꿈하지 않으며, 규칙 학습 카드는 grid `min-width:0`으로 가로 넘침이 없다.

## UX-3 화면 동작 기준 (브라우저 재시험 P4-01~P4-05 수정)

- **업무 시작 차단(P4-01)**: Task 응답의 `block_reasons`(없으면 빈 배열)와 미완료 선행 업무·본업무 전제(`reason`)를 `pages/tasks/blockers.ts`가 모아 목록(막힘 행)과 상세("시작 차단 사유")에 한국어로 보인다. 차단 사유가 있으면 `진행으로 변경`은 비활성이며, 서버가 409로 거절하면 상세를 다시 읽어 최신 사유를 안내(`role="status"`)에 유지한다. 서버가 최종 판정자이고 화면 규칙은 같은 조건(`predecessor_incomplete`는 선행이 모두 완료되면 해소)을 미리 보여 준다.
- **검증 날짜(P4-02)**: 규칙 학습의 검증 시작·끝은 `validationRangeProblem`으로 필수·유효·시작≤끝을 검사한다. 문제가 있으면 입력 가까이 한국어 오류(`role="alert"`, `aria-invalid`)를 보이고 `검증 실행`은 비활성이다. ISO 변환은 검증 통과 뒤에만 한다.
- **검토 오류 소유권(P4-03)**: 검토 화면은 목록 오류(`listError`)와 상세·딥링크 오류(`error`)를 분리한다. 목록 갱신 성공은 상세 오류(권한 없음·없는 검토)를 지우지 못하며, 오류 상자의 `목록으로 돌아가기`로만 해제한다.
- **가로 넘침(P4-04)**: `style.css` 하단의 공통 규칙이 `main` 안의 긴 ID·경로·코드(`overflow-wrap:anywhere`), 폼 요소 `max-width:100%`, grid 자식 `min-width:0`을 보장하고 표·코드는 자체 스크롤 컨테이너에서만 가로 스크롤한다. 단일 열 grid는 `minmax(0,1fr)`을 쓴다. `e2e/responsive-overflow.spec.ts`가 375·520px에서 Main(결과 선택)·Review(상세)·Monitoring·Learning(후보 선택)·Tasks(상세)·Observatory·JudgmentMap의 `document.scrollingElement.scrollWidth ≤ 뷰포트`를 실제 데이터로 단언한다(`E2E_BASE_URL`·`E2E_TENANT`로 대상 지정, 설정 시 기본 웹서버를 띄우지 않는다).
- **내부 코드 한국어화(P4-05)**: `lib/labels.ts`가 판단 항목·질문(`fieldLabel`·`questionLabel`)·출력 유형·검토 사유(`reviewReasonLabel`)·차단 사유·수집 문제·SLO 사유·알림 종류·규칙 결정·근거 위치(`locationLabel`)를 공용 한국어로 바꾼다. 원본 코드·JSON은 `RawDetails`("자세히" `<details>`) 안에만 둔다. 알 수 없는 코드는 원문을 그대로 보인다.

## 대비(color-contrast) 점검 — 라이트·다크 (TOSS-SCREENS)

다크 테마가 OS 설정을 자동으로 따르게 되면서(`docs/architecture/DESIGN_SYSTEM.md` §다크 테마) 대비 점검도 두 테마로 돌린다. 모든 주요 화면(로그인·검토 대기·검토 상세·업무·업무 상세·실행 관찰·판단 맵·규칙 학습·모니터링·정책·평가 라벨)을 1440·375 폭, 라이트·다크, Chromium·WebKit에서 axe `color-contrast`로 검사해 **위반 0건**이다. 이전에 남아 있던 대비 문제의 처리:

- `.eyebrow`: 기본 상태의 axe에서는 라이트 5.24:1로 재현되지 않았다(다크·hover 조합에서 나올 수 있는 쪽을 없앴다): 글자색을 `--color-caption`(라이트 4.77:1, 다크 높음)으로 낮추고 영문 대문자 라벨을 한국어 짧은 라벨로 바꿨다.
- `status-badge` pending: 마찬가지로 기본 상태에서는 재현되지 않았다. 검토 목록의 `nav span` 규칙이 배지 글자색을 caption으로 덮어쓰던 것(배지 고유 색을 잃는 원인)을 배지 밖 요소로 한정해 없앴다.
- 평가 라벨의 확정 버튼 안 `kbd`: 이번 라이트·다크 점검에서 **실제로 나온** 위반(라이트 4.11:1, 다크 2.95:1). 다크에서 글자가 흰색이 되던 것을 `--color-on-primary`로 고정해 해소했다.

화면 CSS에 리터럴 색이 다시 들어오면 `frontend/src/styles/screens-tokens.test.ts`가 실패한다.
