# 실행·배정·관측 계약

버전 0.2 · 2026-10-03 · 상태: 설계 반영, 구현 검증 전

[PRD](../../PRD.md)와 [TASK](../../TASK.md)의 구현 계약이다. SLO 수치와 완료 게이트는 [측정 기준](../spec/05_SLO.md) 및 [완료 조건](../spec/06_ACCEPTANCE.md)을 따른다. 아래 검증 항목은 앞으로 실행할 인수 시험이며 통과 결과가 아니다.

## 쓰기 불변 조건 구현 (2026-10-04)

일반 실행과 재분석 실행은 `start_run_in_tx`에서 Request 잠금, 기대 활성 포인터와 최신 revision 확인, Run·Job 생성, `config_version` 고정, 활성 포인터 변경을 한 트랜잭션으로 처리한다. 재분석 열람 권한도 Request 잠금 후 재검사한다. 이전 `config`·`policy` 버전 키는 읽을 때 호환한다.

업무 배정은 검토 수정 승인 시 `Correction`을 반영한 최종 개발 가능성 분류(수정이 없으면 원 `Judgment`)와 초안 업무의 미해결 전제로 Task의 `block_reasons`를 계산한다. 미해결 가능성 전제와 미정 초안은 승인만으로 해소되지 않는다. `진행` 전이는 남은 차단 사유나 미완료 선행 업무가 있으면 409로 거절한다. 확인 업무가 본업무의 선행 업무로 명시된 경우, 그 확인 업무와 모든 선행 업무의 완료를 확인한 본업무 시작 트랜잭션에서 `feasibility_unresolved`를 해제하고 차단 사유 변경을 감사한다. 초안의 별도 `reason`·미정 상태는 계속 차단한다. 확인 업무가 연결되지 않은 미해결 본업무는 시작할 수 없으므로 검토 초안에서 선행 확인 업무를 명시해야 한다. 자동 배정 eligibility는 판단 시점에 Judgment에 저장하고 배정 시점에는 같은 평가 함수로 재검사한다.

## 1. 자동 배정과 필수 검토

자동 배정은 다음 조건을 **모두** 만족하는 경우에만 허용한다. confidence 하나 또는 `requires_review=false` 값만으로 배정하지 않는다.

| 조건 | 허용 기준 | 충족하지 않을 때 |
| --- | --- | --- |
| 입력과 실행 | 현재 입력 revision의 최신 실행, 문서 포함/제외 선택 확정, 필수 판단·근거·초안 저장 완료 | 보완 또는 실패 상태, 배정 금지 |
| 개발 가능성 | `가능`, 해결되지 않은 데이터·권한·승인·수행 전제 없음 | 조건부 가능·현재 불가·정보 부족은 자동 배정 금지 |
| 판단과 신호 | AI 필요성·개발 가능성·긴급도·담당 조직에 미정 값이 없고 실제 반환된 각 신호가 해당 타입의 정책 기준 충족 | 필수 필드 누락·스키마 위반은 오류, 정보 부족·불확실성은 검토/보완 |
| 업무 초안 | 담당·협업·산출물·선행 조건·근거 유효, 선행 순환 없음, 허용된 조직 범위 | 초안 검증 오류 또는 검토 |
| 필수 검토 | 임상·안전성/약물감시·규제/인허가·긴급 요청에 해당하지 않으며 위험 분류가 확인됨 | 해당 또는 위험 여부 미확정이면 담당 검토자에게 전달 |
| 정책·중복 | 실행에 고정된 정책에서 자동 배정 허용, 배정 이력 없음 | 검토 또는 기존 배정 조회; 새 배정 금지 |

임상·안전·규제·긴급의 필수 검토와 무승인 배정 금지는 서버 불변 규칙이다. Dynamic Config의 초안·게시·되돌리기 모두 이 규칙을 해제하는 설정을 거절한다. 정책 UI에서도 필수 항목을 수정 가능한 체크박스로 표시하지 않는다. 운영 중 더 엄격한 검토/자동 배정 중지 규칙은 추가할 수 있다. 분류 실패를 `위험 없음`으로 바꾸지 않는다.

검토자는 원안과 구분된 수정 초안을 승인할 수 있다. 해결되지 않은 제약이 있는 본업무를 승인만으로 실행 가능하게 만들지 않는다. 제약 해결을 위한 확인 업무는 목적과 담당을 명시하고, 본업무의 시작 차단 조건을 유지한다. 이미 배정된 요청의 재분석은 비교 결과만 남기며 기존 업무 자동 변경이나 추가 배정을 유발하지 않는다.

검증: 높은 confidence의 현재 불가/정보 부족, 읽지 못한 파일의 미확정 선택, 필수 검토 업무, 위험 분류 실패를 각각 넣어 자동 배정 0건 확인. 필수 검토 해제 설정의 게시·rollback 거절, 정상 일반 기술 요청의 정책 허용 배정도 확인한다.

## 2. worker 소유권과 승인 대상

### 소유권과 결과 커밋

Job은 `job_id`, `run_id`, `input_revision`, `owner_id`, `lease_expires_at`, 단조 증가하는 `lease_generation`을 가진다. 인계는 Neo4j 트랜잭션에서 Job을 쓰기 잠금하고 만료/상태를 확인한 뒤 generation을 증가시킨다. lease 비교는 DB 기준 시각을 사용한다.

worker가 단계·결과·이벤트·완료 상태를 쓰거나 heartbeat를 갱신할 때는 **같은 트랜잭션 안에서** Job을 잠그고 owner/generation/미만료/허용 상태를 모두 검증한다. heartbeat는 만료된 소유권을 되살리지 못한다. 검증과 쓰기 사이에 잠금을 풀지 않는다. 인계받기 전 worker가 늦게 반환한 응답은 정식 결과로 커밋하지 않으며, 소유권 상실 진단만 별도 관측 경로에 남긴다.

입력 보완·새 실행 선택은 Request의 `active_run_id`와 revision을 잠금 하에 갱신한다. worker는 실행 자신의 기록을 보존할 수 있지만, 해당 실행이 더 이상 활성 실행이 아니면 요청의 최신 결과 포인터·검토 대상·배정 상태를 바꿀 수 없다. 취소 및 인계 후 terminal 상태를 되돌릴 수 없다.

DB가 사용 불가하면 lease 검증/갱신 및 결과 커밋을 중단한다. 외부 호출 직전에도 소유권을 확인하지만, 이미 전송한 Decision AI 요청을 항상 취소하거나 정확히 한 번만 호출되게 보장할 수는 없다. 재시도별 attempt ID와 사용량을 기록하고 총 deadline·횟수를 제한한다. 보장 대상은 **허용된 결과 커밋과 업무 배정의 중복 방지**다.

### 승인과 배정 트랜잭션

검토 명령은 `(request_id, input_revision, run_id, draft_version, review_version)`과 멱등키를 지정한다. `tenant_id`는 서버 인증에서 결정하는 데이터 격리 범위이며, 그 안의 담당 팀/조직 공유 권한은 별도로 검사한다. 서버는 Request·검토 대상을 정해진 순서로 잠그고 최신 대상 일치, 권한, 초안 유효성, 필수 검토 완료, 기존 배정 여부를 재검증한다. 오래된 화면에서 보낸 결정은 409 충돌로 거절하고 접근 권한이 있는 최신 대상 정보를 반환한다.

승인/수정 승인과 업무·팀/선행 관계·감사·이벤트·멱등 결과의 생성은 한 Neo4j 트랜잭션이다. 자동 배정도 같은 배정 서비스를 통해 1절의 조건을 검증한다. 서버가 정한 배정 식별자는 첫 버전에서 `(tenant_id, request_id)`당 하나이며, 각 업무는 `(assignment_id, draft_task_id)` 유일성을 갖는다. 재분석 ID를 새 멱등키로 사용해 중복 배정할 수 없다. 같은 멱등키의 다른 payload는 충돌이며, 동일 재시도는 저장된 결과를 반환한다. 반환 전에는 현재 조회 권한도 다시 확인한다.

검증: worker A 일시정지→lease 만료→B 인계·완료→A 복귀 순서에서 A의 heartbeat/결과/이벤트 쓰기 거절. 보완 또는 재분석 후 과거 초안 승인 거절. 두 검토자의 동시 승인·승인 응답 유실 후 재전송·worker 재시도에서 배정 1개 및 동일 업무 집합 확인.

## 3. Neo4j 장애와 독립된 관측

Neo4j는 업무 상태의 기준 저장소다. SLO의 요청 분모와 저장 실패를 Neo4j 안의 성공 기록만으로 재구성하지 않는다.

- API 경계와 worker는 Neo4j와 독립된 영속 append-only 관측 journal에 `event_id`, `attempt_id`, 알려진 request/run ID, 수신/응답/단계 시각, 유효성 판정, 상태 코드, 오류 분류, 소요시간을 기록한다. 키·쿠키·원문·모델 전송본문은 기록하지 않는다. 아직 요청 ID가 없을 때도 attempt ID로 진단을 연결한다.
- 개발 환경은 별도 영속 경로의 append+fsync journal과 이를 읽는 독립 수집 프로세스를 사용한다. 다중 writer의 레코드 원자성, 회전·보존·재시작, 성능 영향은 구현과 부하 시험으로 확인한다. 제품 원본 파일 및 Neo4j 데이터 디렉터리와 분리한다.
- 요청 수신과 종료 레코드를 대조한다. DB 장애로 접수 저장이 실패해도 HTTP 실패와 소요시간이 남아야 한다. 수신 후 종료 레코드가 사라진 호출은 성공으로 채우지 않는다. 지원 여부를 장애 때문에 확인할 수 없으면 미확정 표본으로 공개하고 복구 후 근거로 확정한다. 미확정/누락을 숨긴 가용성 통과 판정은 금지한다.
- 수집기와 별도 프로세스의 watchdog이 생산자·수집기의 heartbeat를 감시한다. journal 쓰기 실패/공간 부족과 수집기 정지는 Neo4j나 실패한 journal에 의존하지 않는 watchdog 알림 경로로 전달한다. 수집기 자신만으로 자기 중단을 감지한다고 가정하지 않는다. 호스트 전체 유실을 로컬 journal만으로 복구 가능하다고 주장하지 않는다. 운영 배포에서는 원격 수집·watchdog·알림 수신 경로를 T26에서 검증한다.
- 수신/종료 집계는 attempt ID, 판단 완료는 request/run 식별자로 중복 제거한다. 복구 후 Neo4j의 커밋 결과와 journal을 대조해 누락·불일치를 표시한다. journal을 재생해 승인이나 업무를 실행하지 않는다. 접수·조회 호출 가용성과 요청당 최초 판단 신뢰성의 분모를 구분한다.
- 수집 장애가 발생하면 모니터링을 `관측 불완전`으로 표시하고 해당 구간의 누락·영향을 공개한다. 업무 DB 실패를 `정상 0건`으로 표시하거나, DB에 저장되지 않았다는 이유로 실패를 분모에서 제외하지 않는다.

검증: Neo4j 중단 중 유효 요청 접수/조회 실패의 attempt·응답·지연이 journal과 집계에 남는지, 저장소 오류에서 진단으로 이동하는지 확인한다. journal 수집 정지 및 쓰기 실패를 별도로 주입하고 독립 알림·관측 불완전 표시·복구 후 중복 없는 대조를 확인한다.

## 4. 최초 판단과 정보 보완 측정

정의의 기준은 [05_SLO의 보완·재실행 규칙](../spec/05_SLO.md#보완재실행과-측정-단위)이다. 지원 범위 입력은 업무 정보가 부족해도 현재 입력에 대한 실제 판단을 수행한다. 필수 분류와 근거·부족 정보·검토 사유가 모두 저장되어 사람이 판단을 검토할 수 있어야 최초 판단 완료다. 추가 질문만 생성하거나 상태를 `보완 필요`로 바꾸는 것은 완료가 아니다.

정보 부족/판단 보류는 실제 판단값으로 보존하며 미확정 담당·업무를 추측해 채우지 않는다. 해당 필드에는 미정 상태와 사유를 저장하고, 검토 책임자 배정과 모델의 업무 담당 판단을 구분한다. 완전한 판단 기록을 얻지 못했다면 기존 120초 실패 기준을 유지한다. 보완 대기는 판단 저장 후 별도로 관측하며 기존 SLO 시계를 일시정지하지 않는다.

검증: 지원 범위의 정보 부족 요청에서 실제 판단 기록이 먼저 저장되고 사용자 답변 대기는 별도 표시됨을 확인한다. 120초 초과 후 재시도 성공, 수시간 후 보완, 부분 파일 실패를 각각 넣어 최초 요청의 실패/시작 시각이 지워지거나 분모가 늘어나지 않는지 대조한다.

## 5. 작업 소유권과 선행 관계

T11이 검토 결정 **및 배정 트랜잭션**을 모두 구현·검증한다. T12는 T11이 만든 업무의 조회·필터·상태 변경·선행 막힘 표시 API를 담당한다. T11의 중복 배정 시험은 T12의 API/UI 없이 실제 저장 결과로 수행할 수 있어야 한다. T04의 데이터/잠금/유일성 기반 위에서 T11→T12→T13 순서로 진행한다.

## 6. WebMCP 사전 확인

M0의 T00에서 공식 초안과 실제 사용할 브라우저/버전·설정·호출 주체를 확인하고, 최소 읽기 도구의 등록과 실제 호출 증거를 남긴다. 브라우저 전용 기능은 JavaScript 모의 객체나 서버 MCP로 대체하지 않는다. 미지원 브라우저에서도 기본 페이지가 정상 동작하는지 확인한다.

환경을 확보하지 못하면 T00과 G10의 해당 부분을 차단으로 기록한다. 독립적인 백엔드/화면 구현은 진행할 수 있으나 M0의 호환성 확인을 완료로 보고하지 않는다. T20은 T00 결과를 바탕으로 실제 제품의 요청/Trace 및 권한을 통합하고 G10 전체를 검증한다.

## 8. 규칙 수명·적용과 판단 관계

규칙 후보는 제안·검토 필요·자료 부족 상태에서 실행에 영향을 주지 않는다. 규칙 관리자는 사유를 남겨 승인(범위 확정/수정), 기각, 검증, 게시, 중단, 되돌리기를 수행하며 각 결정과 권한 검사를 감사 기록으로 남긴다. 검토자의 단건 승인·수정 승인은 해당 요청의 `ReviewDecision`과 `Correction`을 생성할 뿐 규칙 상태를 바꾸지 않는다. 규칙 제안·검토·실행 권한은 [08_LEARNING_LOOP 4절](../spec/08_LEARNING_LOOP.md#4-규칙-수명과-권한)의 역할 정의를 따른다.

검증하지 않은 후보는 게시할 수 없다. 게시·중단·되돌리기는 모두 감사·이벤트와 함께 새 Dynamic Config 버전을 만드는 트랜잭션이다. 기존 설정이 허용하는 범위에서만 규칙을 저장하고, 1절의 임상·안전·규제·긴급·위험 미확정 필수 검토, 무승인 배정 금지, 불가/정보 부족 자동 배정 금지 조건을 약화하는 규칙의 저장·게시·되돌리기를 거절한다. 더 엄격한 검토 전환은 허용한다.

검증: 권한별 상태 전이와 사유 필수 여부를 확인하고, 미검증 후보 게시 및 불변 조건 약화 규칙의 저장·게시·되돌리기가 거절되는지 확인한다. 단건 수정 승인 후 `Correction`은 생성되지만 규칙 상태와 Config 버전은 바뀌지 않는지 대조한다. 게시·중단·되돌리기마다 새 Config 버전, 감사 기록, 이벤트가 함께 커밋되는지 확인한다.

각 실행은 시작 시 Dynamic Config 버전과 그 버전에 포함된 규칙 버전을 고정하고 그 버전의 규칙만 사용한다. 실행 단계의 결과와 `RuleApplication` 기록(사용·범위 밖 미사용·충돌 미적용, 규칙 버전, 변경 전후 값)은 2절의 소유권 검증과 같은 트랜잭션에서 쓴다. 규칙 적용 결과를 과거 실행에 소급하지 않으며 중단·되돌리기는 이후 시작한 실행에만 영향을 준다.

검증: Config 게시 직전/직후 실행을 병렬 시작해 각 실행이 시작 버전만 사용하는지, 진행 중 실행이 이전 버전을 유지하는지 확인한다. 만료·인계된 worker가 단계나 `RuleApplication`을 기록할 수 없는지, 정상 소유자가 단계 결과와 적용 기록을 원자적으로 커밋하는지 확인한다. 사용·범위 밖·충돌 사례의 버전과 전후 값을 실행 기록과 대조한다.

섀도 비교 실행은 별도 실행 종류로 분리하고 저장된 모델 반환값을 기준/후보 규칙으로 재평가하는 것을 기본으로 한다. 업무·배정·검토 큐·알림·사용자 이벤트·최신 결과 포인터를 생성하거나 변경하지 않는다. 컨텍스트 규칙에 한해 Decision AI 재호출을 허용할 수 있으며 호출 상한·비용을 기록한다. 섀도 결과는 SLO 분모에 포함하지 않고 규칙 효과 지표로 별도 공개한다.

검증: 섀도 실행 전후 업무·배정·검토 대상/큐·알림·사용자 이벤트·최신 결과 포인터의 카운트와 값을 비교해 변화가 0인지 확인한다. 실행 종류가 섀도로 분리되고, Decision AI 재호출이 있는 경우 설정 상한과 호출 수·비용이 기록되는지 확인한다. SLO 집계에서 섀도 실행이 제외되고 별도 효과 보고에 나타나는지 대조한다.

판단 관계는 `EvidenceSpan`·`ModelOutput`·`Correction`·`RuleCandidate`·`RuleDecision`·`ReviewDecision`·`RuleVersion`·`ValidationRun`·`RunStep` 등 실제 엔터티가 생성되는 시점에 해당 생성 트랜잭션으로 저장한다. `APPLIED`는 `RuleApplication`을 나타낸다. 저장되지 않은 중간 관계를 사후 합성하지 않으며 tenant 경계와 원문 권한을 동일하게 적용한다.

검증: 각 엔터티 생성 트랜잭션과 관계 저장 결과를 대조하고, 트랜잭션 실패/재시도 뒤 고아·중복 관계가 생기지 않는지 확인한다. 그래프 조회 결과와 화면의 노드·관계가 일치하고 존재하지 않는 중간 관계를 렌더링하지 않는지, tenant 및 원문 권한 밖 조회가 차단되는지 확인한다. 새로고침·서버 재시작 후 후보·결정·버전·검증·적용 관계가 유지되는지 확인한다.
