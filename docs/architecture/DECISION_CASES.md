# 판단 사례 (암묵지 자산화)

검토자가 AI 분류를 고친 판단을 사유와 출처를 붙여 `DecisionCase`로 남기고, 이후 검토에서 참고 선례로 다시 보여 준다. 이 기능은 사람의 정체성을 복제하지 않는다. 업무 판단 기준을 근거와 함께 쌓고 다시 쓰는 기능이다. 모델 학습이나 파인튜닝도 아니다. 사례는 Decision AI 프롬프트에 들어가지 않고, 판단값을 자동으로 바꾸지 않으며, 어떤 실행 권한도 주지 않는다.

## 적용 대상

- 판단하는 사람: 검토자. AI 원안의 `ai_need`·`feasibility`·`urgency`·`lead_org`를 수정 승인한다.
- 기존 공백: 수정 사유는 `Correction`에 남지만, 규칙 후보 → 섀도 검증 → 게시를 거쳐야만 다시 쓰였다. 그 전에는 다른 검토자가 같은 상황을 만나도 앞선 판단을 볼 수 없었다.
- 기대 개선: 같은 AI 원안이 나온 요청에서 앞선 판단과 그 조건·예외를 바로 확인한다. 판단 일관성과 사용자 수정량은 `consulted`·`followed` 집계로 관찰한다.

## 저장 단위

| 항목 | 출처 | 비고 |
| --- | --- | --- |
| 상황 | 요청 마스킹 제목, AI 원안 값 | 기록 사실 |
| 선택지·판단 | 필드 허용값, 검토자 수정값 | 기록 사실 |
| 근거 | 검토자가 적은 결정 사유 | 사용자 명시. 저장 시 마스킹 |
| 적용 조건·예외 | 검토자가 직접 입력한 키워드 | AI 추정 없음 |
| 결과 | 검토자가 기록한 `held`/`failed`와 메모 | 승인과 별개 신호 |
| 출처 | `correction_id`, `review_decision_id`, `request_id`, `run_id`, `revision_id` | `(DecisionCase)-[:FROM]->(Correction)` |
| 상태 | `recorded` → `confirmed` → `verified`, `retired` | 버전·이력·감사 기록 |
| 소유·권한 | `owner`, 원 요청의 `org_ids` | 조회는 `rule:read` 범위 |

## 흐름

1. 수정 승인 트랜잭션에서 분류 필드 `Correction`마다 사례를 `recorded`로 만든다.
2. 검토 상세(`GET /api/reviews/{id}`)의 `precedents`가 필드별로 사례를 고른다. 조건: 같은 tenant, 조회 권한 있음, 폐기 안 됨, 원본 `Correction` 존재, AI 원안 값이 같음.
3. 적용 판단:
   - 예외 키워드가 있으면 `excepted`(적용 금지)로 표시한다.
   - 조건이 없으면 `unconfirmed`(참고만)로 표시한다.
   - 조건 키워드가 있으면 `applies`, 없으면 숨기고 `hidden_unmet`으로 센다.
   - 함께 표시: 오래된 사례(180일 초과), 선례끼리 결론이 다를 때 `conflict`, 필드당 최대 3건.
4. 검토자가 "이 값으로 채우기"를 눌러야만 입력값이 바뀐다. 승인 시 보여 준 사례 ID(`consulted_case_ids`)와 최종값 일치 여부를 `(ReviewDecision)-[:CONSULTED {followed}]->(DecisionCase)`로 남긴다.
5. `/cases` 화면과 `POST /api/cases/{id}/{confirm|outcome|retire|revert}`에서 조건 확인, 결과 기록(`failed`는 폐기), 폐기, 이전 버전 되돌리기를 한다. 낙관적 버전 검사(409)와 감사 기록을 쓰고, 권한은 검토자·규칙 관리자다.

## 보안·삭제

- 모든 질의는 tenant로 한정한다. 조직 범위 밖 사례는 조회·수정 모두 404를 반환한다.
- 원문 열람 권한이 없으면 일치한 키워드를 숨긴다.
- 요청 원문은 키워드 일치 검사에만 쓴다. 원문 속 지시문은 사례 상태나 판단을 바꾸지 못한다.
- 원본 `Correction`이 삭제되면 사례는 조회·재사용에서 빠진다. 별도 검색 인덱스나 캐시는 없다.
- 내보내기·가져오기는 공유 필요가 확인되기 전까지 구현하지 않는다.

## 검증

`backend/tests/integration/test_decision_cases.py`가 실제 Neo4j에서 다음을 확인한다.

- 출처 연결과 마스킹
- 조건 일치·불일치·예외, 새 상황에서 선례 없음
- 충돌과 오래된 사례 표시
- 참고·따름 기록이 결과와 분리되는지
- 버전 충돌, 폐기, 되돌리기
- 조직·tenant·역할 격리, 원문 권한별 키워드 숨김
- 악성 지시문, 원본 삭제
- HTTP API

화면 동작은 `frontend/src/pages/Review.test.tsx`와 `Cases.test.tsx`가 확인한다.

## 확장 시점

- 조건 키워드 대신 의미 검색: 키워드 미일치로 숨겨진 사례가 실제로 관련 있었다는 수정 기록이 쌓일 때
- 사례를 규칙 후보로 승격: 같은 결론의 `verified` 사례와 높은 `followed` 비율이 확인될 때
- 사례를 판단 모델 컨텍스트로 쓰기: 섀도 비교로 이득이 확인될 때
