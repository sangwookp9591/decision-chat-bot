00한눈에 보기

쉽게 말하면

병원 응급실의 분류(triage) 창구와 비슷합니다. 환자(업무 요청)가 오면 간호사(AI, Decision AI)가 먼저 증상을 보고 급한지, 어느 과로 보낼지 판단합니다. 애매하거나 위험하면 의사(검토자)가 직접 확인하고, 확인이 끝나야 담당 과(팀)에 업무가 배정됩니다. 모든 과정은 기록장(그래프 DB)에 남고, 운영자는 CCTV(관측 화면)로 어디서 막혔는지 봅니다.

01전체 아키텍처

쉽게 말하면

식당으로 생각하면 쉽습니다. 손님(브라우저)은 카운터(API)에 주문을 넣고, 카운터는 주문서를 장부(Neo4j)에 적은 뒤 주방(worker)에 초인종(Redis)을 울립니다. 주방은 전문가(Decision AI)에게 물어 요리를 만들고, 진행 상황은 카운터를 통해 손님 화면에 실시간으로 나갑니다. 장부가 망가져도 카운터 옆 출입 기록(journal)은 따로 남아서 “몇 명이 왔다가 실패했는지” 셀 수 있습니다.

계층 규칙

코드는 api(라우터) → service → store → db 방향으로만 의존합니다. 공통 타입과 규칙은 domain에 둡니다. 이 방향은 import-linter 계약 6개로 강제되며, 위반하면 make lint가 실패합니다. 모든 DB 질의는 TenantTx를 거쳐 tenant 조건이 자동으로 붙습니다.

02요청 하나의 실행 흐름

쉽게 말하면

주문하자마자 영수증(요청 카드)이 바로 나옵니다. 0.5초쯤 뒤에는 “아마 이런 요리일 거예요”라는 잠정 안내(잠정 판단)가 먼저 나오고, 곁들임(근거)과 조리 순서(업무 분해)는 두 요리사가 동시에 준비해서 자리마다 채워 넣습니다. 마지막에 확정 도장(최종 판단)이 찍힙니다.

시간은 Astra 실제 브라우저 측정(실제 Decision AI, 텍스트 요청 p50)입니다. 첨부가 있으면 추출 시간만큼 늘어납니다(최종 p50 약 2.4초).

단계별 기록

각 단계는 RunStep으로 저장되어 실행 관찰 화면의 Flow, Trace, 재생(Play)에 그대로 쓰입니다. 재생은 저장된 기록만 읽고 모델을 다시 부르거나 업무를 바꾸지 않습니다.

04검토와 배정

쉽게 말하면

검토자가 AI 의견을 고쳐도 원래 의견은 지우지 않고 옆에 남깁니다. 두 검토자가 동시에 승인 버튼을 눌러도 업무는 한 번만 만들어집니다. 오래된 화면에서 누른 승인은 “내용이 바뀌었어요” 안내와 함께 거절됩니다.

05규칙 학습 순환

쉽게 말하면

검토자들이 같은 방향으로 자주 고치는 패턴이 보이면, 시스템이 “앞으로 이렇게 하면 어떨까요?”라는 후보를 만듭니다. 규칙 관리자가 승인하고, 실제 업무에 영향을 주지 않는 연습(섀도 검증)을 거친 다음에야 게시합니다. 모델을 다시 학습시키는 것이 아니라, 정해진 규칙과 참고 문장을 판단에 덧붙이는 방식입니다.

06해결 ① 판단 결과를 답답하지 않게

쉽게 말하면

예전에는 요리를 전부 완성할 때까지 손님 앞에 아무것도 내놓지 않았습니다. 지금은 주문 즉시 영수증을 주고, 메인 요리를 먼저 내놓은 뒤 곁들임을 차례로 채웁니다. 전체 시간도 줄었지만, 그보다 “기다리는 동안 아무것도 안 보이는 시간”이 크게 줄었습니다.

이전

  • Decision AI 분류 → 근거 연결 → 업무 분해를 순서대로 모두 끝낸 뒤 한 번에 저장
  • 화면은 저장 완료 이벤트를 받은 뒤 다시 조회
  • 사용자는 약 2초 이상 결과를 하나도 보지 못함

이후

  • 핵심 분류 직후 잠정 판단을 저장하고 이벤트로 즉시 전송
  • 근거 연결과 업무 분해를 병렬 실행, 근거 질문도 최대 4개 병렬
  • 영역별로 최종 모양 스켈레톤을 두고 도착하는 대로 채움

적용한 원칙과 출처

원칙출처이 프로젝트에서
데이터가 필요한 영역마다 로딩하고 최종 모양의 폴백을 보여줌토스페이먼츠 초기 렌더링판단 카드·근거·업무 영역을 따로 채움, 위치 이동 0px
짧은 로딩(약 200ms 이내)은 로딩 표시를 생략토스 Suspensive DelayuseDelayedFlag 훅으로 깜빡임 방지

07해결 ② 모니터링 첫 진입

쉽게 말하면

계기판 네 개가 모두 켜질 때까지 운전석 화면 전체를 가려 두고 있었습니다. 이제는 화면 틀을 바로 보여주고 준비된 계기판부터 켭니다. 계기판 계산 자체도 같은 질문이 동시에 여러 번 들어오면 한 번만 계산해서 나눠 주도록 바꿨습니다.

08해결 ③ 다중 인스턴스 실시간 전달

쉽게 말하면

카운터가 여러 개 생겨도 모든 손님이 같은 소식을 받아야 합니다. 초인종(Redis)은 “새 소식 있음”만 알리고, 소식 내용은 늘 장부(Neo4j)에서 순번대로 읽습니다. 초인종이 고장 나도 5초마다 장부를 확인하니 소식을 놓치지 않습니다.

10해결 ⑤ 멈춘 프로세스가 쥔 잠금

쉽게 말하면

한 요리사가 냉장고 문을 잡은 채 얼어붙으면, 다른 요리사는 영원히 기다려야 했습니다. 이제 문을 잡을 수 있는 시간에 한도를 두어, 한도가 지나면 문이 저절로 풀리고 다른 요리사가 이어서 일합니다.

sequenceDiagram
  participant A as worker A
  participant DB as Neo4j
  participant B as worker B
  A->>DB: 쓰기 트랜잭션 시작(Job 잠금)
  Note over A: 프로세스 정지(SIGSTOP)
  B->>DB: Job 확보 시도
  Note over DB: 이전: 잠금 무한 대기
이후: 트랜잭션 7초 · 잠금 6초 한도
  DB-->>A: 트랜잭션 강제 종료, 잠금 해제
  B->>DB: lease 만료 Job 확보(generation +1)
  B->>DB: 판단 완료·저장
  Note over A: 재개 후 쓰기 시도
  A->>DB: heartbeat · 결과 쓰기
  DB-->>A: 거절(소유권 상실)

앱 트랜잭션에도 기본 제한 시간을 두고, 보존 정리나 스키마 변경처럼 오래 걸리는 작업만 별도로 늘립니다. 장애 시험 11종이 두 번 연속 통과했습니다.

11해결 ⑥ 계층 규칙과 tenant 강제

쉽게 말하면

건물의 층마다 오갈 수 있는 계단을 정해 두고, 규칙을 어기면 문이 열리지 않게 했습니다. 또 모든 서랍(질의)에 회사 이름표(tenant)가 자동으로 붙어서, 다른 회사 서랍을 실수로 여는 일이 구조적으로 막힙니다.

import-linter 계약

대형 Python 모놀리스를 계약 40개 이상으로 관리하는 Kraken 사례를 따랐습니다. 계약 6개, 위반 0건, 호환용 예외 1건(사유 기록)입니다.

TenantTx

Neo4j Community에는 Row-Level Security가 없어서(AWS의 RLS 설명) 같은 원칙을 드라이버 래퍼로 구현했습니다. tenant 자동 주입, 시험 모드의 tenant 없는 질의 거부, 교차 tenant는 사유 기록 경로로만 허용합니다.
