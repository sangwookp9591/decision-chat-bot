## FIX-SSE 원인과 개선 확인

기존 SSE 코드는 연결별 0.5초 폴링으로 20연결에서 빈 구간에도 이벤트 조회 약 40회/초를 실행했다. 각 요청 이벤트를 전달할 때 Request 메타데이터를 별도 질의했으므로, 공식 30분 측정 구간의 `sse_deliver` 요청 이벤트 851,158건은 같은 수의 Request 조회를 유발했다. 공식 구간의 전달 지연은 851,158표본에서 p50 657ms, p95 2,000ms, max 17,941ms였다. Event 조회는 `tenant_id`와 `seq`를 조건으로 사용하며, Neo4j 5.26 `EXPLAIN`에서 `event_tenant_seq` RANGE 인덱스의 `NodeIndexSeek`를 확인했다. 전체 라벨 스캔이 병목이라는 가설은 이 실행 계획과 맞지 않는다.

개선 후에는 API 프로세스마다 tenant별 폴러 1개가 0.2초 간격으로 조회한다. 2프로세스의 정상 빈 구간 이벤트 조회는 설정상 약 10회/초다. 비어 있지 않은 배치는 request ID 집합을 한 번의 Cypher로 읽고 연결별 권한을 검사한다. 정상 상태 10분 기준 이벤트 조회는 약 6,000회와 초기 따라잡기 조회이며, Request 메타 조회는 비어 있지 않은 배치당 최대 1회다. 이는 코드 경로와 설정에서 계산한 질의 수이며 Neo4j 서버의 실제 실행 질의 수를 직접 수집한 값은 아니다. 비교 대상으로 이전 10분 환산 Request 조회는 약 283,719회다. 통합 시험의 10개 동시 연결에서 이벤트 조회·메타 조회 각각 10회 미만임을 계측했다.

부하 중 1,000건 배치를 20회 조회한 간단한 프로파일에서 `list_events` 중앙값 149.45ms/p95 260.04ms, 서로 다른 Request 74건의 일괄 메타 조회 중앙값 18.24ms/p95 52.41ms였다. SSE 프레임 10,000회 직렬화는 건당 평균 0.0116ms였다. 큰 배치 DB 조회와 연결별 journal fsync가 남은 비용이며, 직렬화 자체는 주요 병목으로 보이지 않는다. 이 프로파일은 부하 실행 중 별도 클라이언트에서 측정했으므로 서비스 요청의 단독 지연으로 해석하지 않는다.
